# MCP rebuild lifecycle under OTP

Status: planning; implementation authorized by user, pending independent plan review and mandatory TLA+ gate.
Epic: `bd-mcp-rebuild-lifecycle-gbi9`. Base: master `2ba68d6640c40ae254cfeee60dc84432b2f600f5` (standalone epic; implementation in `.state/worktrees/`).

## Problem and boundary

`kb_rebuild` currently casts `PortManager.rebuild_async/0`, which launches `sh -c ... &` and immediately reports that rebuild started. The shell double-fork deliberately leaves `kb rebuild` alive after BEAM exit; OTP cannot observe completion, prevent duplicate jobs, or terminate it. Keep Rust responsible for event-log replay, locking, and index/SQLite computation. Elixir owns the child lifecycle. Preserve all 17 MCP tools and the Option B repository/OS-credential boundary; no package authorization or new dependency.

## Contract

1. `kb_rebuild` remains a no-argument tool with no new public fields. Its existing successful immediate acknowledgment text is emitted only after a synchronous internal launch call has accepted an already-running attempt or successfully opened one child. A failed executable/port launch returns an MCP tool error, not a false “started” result. The acknowledgment does not claim successful completion. With no database, retain the existing init hint and launch nothing.
2. A dedicated OTP-supervised rebuild owner launches the Rust rebuild worker directly through an Erlang `:use_stdio` port, without shell, background ampersand, or detached process. A rebuild-only Rust leaf guard arms an inherited-stdin EOF reader **before** ready/work; EOF exits the worker. The owner observes exit status and drains stdout/stderr without unbounded memory or log growth; the existing `rebuild.log` path may be retained with a documented size cap/rotation. The normal `kb mcp` request port remains available while rebuild runs.
3. Bind the worker to **the same database, event log, and lock** as the active `kb mcp --db` port, including canonical layout, explicit `KB_DB_PATH`, and adjacent legacy event/lock fallback. Current `kb rebuild` discovers from cwd and has no `--db`, so merely deriving a working directory by dropping two path components is insufficient. A narrow Rust CLI `--db`/explicit-path change is allowed if necessary; reuse the same path-resolution rule as MCP and keep Rust's replay/index algorithm unchanged. Do not dispatch rebuild over the long-lived synchronous MCP Rust port, which would block ordinary reads.
4. At most one active rebuild per MCP application. Concurrent `kb_rebuild` calls coalesce into that attempt and receive the same acknowledgment. Once the prior child has exited **and termination has been observed**, a later explicit request may start a fresh attempt. No automatic retry: Rust already bounds internal prefix/checkpoint retries, and a nonzero exit can follow partial durable work. Report completion/failure to logs; do not silently claim completion.
5. Provide private Elixir `start`, `cancel`, and status operations (no new MCP method). `start` synchronously accepts an already-running attempt or opens one child; `cancel` closes its port/stdin and waits for observed OS exit before clearing the active slot or permitting a fresh attempt. A later explicit `start` is the only retry. Shutdown/cancellation must not leave a worker after normal MCP stdin EOF (`McpServer` calls `System.halt/1`), owner crash, or BEAM termination. Real-process tests must capture child OS PID and check liveness with a bounded wait; Port.info/1 or an Erlang process monitor alone is insufficient.
6. The existing Rust rebuild data-format and transactional behavior remain unchanged. No Rust coordination layer, OPA, package authorization, public cancellation method, or new dependency is introduced.

## Design risk and decision

The direct-port probe showed owner normal stop and `:kill` terminate the child, but whole-BEAM `System.halt(0)` leaves it alive after two seconds. The selected fix is a **rebuild-only inherited-stdin EOF guard** in Rust, with no new dependency or Linux-only process API. A temporary standalone Rust worker armed the guard before reporting ready; with `Port.open(..., [:use_stdio, ...])`, it remained alive without EOF while idle, then observed EOF and its OS PID/start-time identity died within two seconds after owner normal stop, owner `:kill`, `System.halt(0)`, and external BEAM SIGKILL. This is an implementation viability probe, not a substitute for packaged regression tests. The production guard must arm before rebuild work begins; a premature EOF must fail/exit rather than continue. Elixir remains the sole job coordinator; Rust keeps only its existing rebuild computation plus this lifetime guard. Do not infer exact path binding from cwd; the Rust MCP worker already has explicit `--db` plus adjacent event/lock fallback, while standalone rebuild currently has neither.
